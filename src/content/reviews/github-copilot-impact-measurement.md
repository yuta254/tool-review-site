## この記事の結論

GitHub Copilot の導入効果は、**「どれだけ使われているか」と「開発の成果が変わったか」を分けて**測るのが基本です。

- **使われているか**は、GitHub公式のダッシュボードとAPIでかなり細かく見られる(利用者数、提案の採用率、使っている機能など)。
- **成果が変わったか**は、公式の指標だけでは決まらない。GitHub自身が、プルリクエストとの関係は「関連を示すもので、因果の証明ではない」と書いている。
- そのため、**導入前の数字を取っておく → 一部のチームで試す → 同じ物差しで比べる → アンケートで補う**、という順番で測るのが現実的です。

この記事は GitHub の公式ドキュメント(docs.github.com)を2026年10月21日に確認して整理したものです。ダッシュボードの名前や項目は更新されることがあるため、実際に設定するときは公式ドキュメントの最新版を確認してください。

## GitHubが公式に用意している測る仕組み

GitHub のドキュメントでは、Copilot の利用状況を見る手段として次のものが挙げられています。

| 仕組み | 内容(公式ドキュメントの説明の要旨) |
| --- | --- |
| Copilot usage metrics ダッシュボード | 企業(Enterprise)とその配下の組織について、直近28日の利用の推移を見る |
| Code generation ダッシュボード | 利用者やエージェントがどのようにコードを生成しているかを見る |
| Copilot impact ダッシュボード | 利用の深さ(段階)ごとの利用者と、プルリクエストの数・マージまでの時間の関係、ROIの推計を見る |
| Copilot usage metrics API | 企業・組織・リポジトリ・ユーザー単位のデータを取得する(公式は「主に開発・保守しているAPI」と説明) |
| NDJSON 形式の書き出し | 生データを自社の分析ツールや長期保存に回す |
| ユーザー管理 API | ライセンス(シート)の情報。利用状況のデータには含まれないので、こちらで取る |

ダッシュボードは、企業アカウントの **Insights タブ → Copilot usage** から開く形で説明されており、事前に「Copilot usage metrics」のポリシーを有効にする必要があります。データは日付が締まってから**2〜3日ほど遅れて**反映されると書かれています。

## 見られる主な指標

| 分類 | 主な指標 |
| --- | --- |
| 利用の広がり | 日次・週次・月次のアクティブユーザー数、Copilot のコードレビューを使った人数 |
| 利用の深さ | 利用の段階(コード補完が中心の段階 → エージェントが中心の段階 → 複数エージェントの段階)ごとの人数 |
| 利用の中身 | チャットのモード別のリクエスト数、エージェントを使った人の割合 |
| 提案の採用 | コード補完の採用率(提案がどれだけ受け入れられたか) |
| コード量 | 提案された行数、追加・削除された行数 |
| プルリクエスト | 作成数・マージ数、マージまでの時間の中央値、Copilot が作ったプルリクエストとの比較 |

公式の解説では、目安として「週次アクティブユーザーがライセンス数の60%を超えていれば、継続的に使われている」と書かれています。

## 見誤りやすい点(GitHub自身が書いている注意)

公式ドキュメントには、数字の読み方についての注意がはっきり書かれています。導入効果を報告するときに特に大事なものを挙げます。

1. **採用率は生産性そのものではない。** 採用率の上昇は「信頼と有用性が高まっている」兆候として扱われており、作業が速くなった証拠ではありません。
2. **プルリクエストとの関係は因果ではない。** impact ダッシュボードの「よく使う人と、あまり使わない人の比較」は、別々の人の集団を比べたものです。GitHub は、チームの構成・案件の難しさ・経験年数が Copilot と同じくらい結果に影響しうると書いています。
3. **よく使う人のマージ数が少なくても、価値が低いとは限らない。** 大きく難しい仕事をしている可能性がある、と説明されています。
4. **IDEの送信設定(テレメトリ)が切れている人は数字に出にくい。** 多くの指標はIDE側から送られるデータに頼っています。また、GitHub.com 上や GitHub Mobile での Copilot Chat の利用は含まれません。
5. **組織の数字を足しても企業全体の数字にはならない。** 1人が複数の組織にいると、組織ごとの数字には重複して出ますが、企業全体では1人として数えられます。
6. **ROIは推計。** impact ダッシュボードのROIは、正確な財務結果ではなく推計だと書かれています。

## 導入前後の比べ方(手順)

公式の指標を使いながら、因果を取り違えないための手順です。

1. **導入前の数字を取っておく。** プルリクエストのマージ数(1人あたり・月あたり)、マージまでの時間、レビューで差し戻された回数など、Copilot と関係なく取れる数字を、導入前の2〜3か月分残しておきます。導入後に始めると比べる相手がいません。
2. **一部のチームから始める。** 全員に一斉に入れると、季節要因(繁忙期、リリース前など)と区別できません。似た仕事をしているチームを2つに分けて、先に入れるチームと後から入れるチームを作ると比べやすくなります。
3. **同じ物差しで比べる。** 比べる期間・チーム・案件の種類をそろえます。GitHub も、ROIを期間で比べるときは同じ給与帯で比べるよう書いています。
4. **利用が定着したかを先に確かめる。** 週次アクティブユーザーがライセンス数に対して低いままなら、成果を論じる前に、設定・研修・ライセンスの割り当てを見直す段階です。
5. **アンケートや振り返りで補う。** GitHub も、ダッシュボードの傾向をアンケートや振り返りと組み合わせることを勧めています。「どの作業が楽になったか」「かえって手間が増えた作業はあるか」を聞くと、数字の理由が分かります。

## 報告で使うときのまとめ方の例

- **使われているか**:週次アクティブユーザー ÷ ライセンス数、利用の段階ごとの人数の推移
- **成果が変わったか**:導入前と比べた、プルリクエストのマージ数とマージまでの時間(先に入れたチームと後から入れたチームの差も併記)
- **限界**:「関連であって因果ではない」「テレメトリが切れている人は含まれない」を明記する

数字だけを並べると、採用率の高さがそのまま「生産性が上がった」と読まれがちです。何を測った数字で、何は分からないのかを一緒に書くと、判断を誤りにくくなります。

## よくある質問

**Q. 個人のプランでもダッシュボードは使えますか。**
この記事で確認した公式ドキュメントは、企業(Enterprise)や組織の管理者が使う前提で書かれています。個人で使っている場合の確認方法は、GitHub の最新のドキュメントを確認してください。

**Q. 提案の採用率は何%なら良いのですか。**
公式ドキュメントでは採用率の合格ラインは示されておらず、上がっていれば信頼と有用性が高まっている兆候、という読み方が示されています。言語や作業内容で大きく変わるため、他社の数字と比べるより、自社の推移を見る方が意味があります。

**Q. ほかのAIコーディングツールと比べるには。**
ツールごとに取れる指標が違うため、同じ物差しで比べるには、プルリクエストの数やマージまでの時間など、ツールに依存しない数字を使います。ツールそのものの違いは[GitHub Copilotレビュー](/reviews/github-copilot-review/)と[AIコーディングツールの比較](/reviews/ai-coding-tools-comparison/)を参照してください。
