## この記事の結論

GitHub Copilot の導入効果は、**「どれだけ使われているか」と「開発の成果が変わったか」を分けて**測るのが基本です。

- **使われているか**は、GitHub公式のダッシュボードとAPIで細かく見られる(日次・週次の利用者数、コード補完の採用率、AIで追加・削除された行数、利用の段階など)。データはその日が終わってから **UTCで丸2日以内**に反映される。
- **成果が変わったか**は、公式の指標だけでは決まらない。GitHub自身が、プルリクエストとの比較は「関連を示すもので、導入が生産性を変えた証明ではない」と書いている。
- GitHubの公式ガイドは、**導入を変える前に基準の数字を記録する**こと、**同じチーム・同じ期間で比べる**こと、**アンケートや振り返りと組み合わせる**ことを勧めている。
- 公式の解説では、週次アクティブユーザーがライセンス数の**60%を超えていれば、継続的に使われている目安**とされる(目標値として扱わないよう注記あり)。
- API の1日ごとの企業・ユーザーのレポートは**2025年10月10日以降の分があり、今日から最長1年さかのぼれる**。導入前の数字を残すなら、Copilot と関係なく取れるプルリクエストの数字を別に保存しておく必要がある。
- 組織向けの席の料金は Business 1席月19ドル・Enterprise 1席月39ドル。10席を1年使うと、Business で税込2,508ドル(1ドル=150円で約376,200円)になり、効果を報告するときの費用の側の数字になる。

この記事は GitHub の公式ドキュメント(docs.github.com)を2026年11月23日に確認して整理したものです(初版は10月21日確認)。当サイトでは実機・実サービスを検証していません。導入の結果の数字は載せず、公式に書かれている指標の定義と測り方の手順だけを並べます。ダッシュボードの名前や項目は更新されることがあるため、実際に設定するときは公式ドキュメントの最新版を確認してください。

## GitHubが公式に用意している測る仕組み

| 仕組み | 内容(公式ドキュメントの説明の要旨) |
| --- | --- |
| Copilot usage metrics ダッシュボード | 企業とその配下の組織について、直近28日の利用の推移を見る |
| Code generation ダッシュボード | 利用者やエージェントがどのようにコードを生成しているかを、IDEで追加・削除された行数で見る |
| Copilot impact ダッシュボード | 利用の段階(コホート)ごとの利用者と、プルリクエストのマージ数・マージまでの時間の関係、ROIの推計を見る |
| リポジトリのインサイト | 組織のリポジトリのプルリクエストの動きと、Copilot のコードレビューの結果を見る。サーバー側のデータで、IDEのテレメトリに頼らない |
| Copilot usage metrics API | 企業・組織・リポジトリ・ユーザー単位のレポートを取得する。レポートそのものではなく、期限つきのダウンロード用URLが返る |
| NDJSON 形式の書き出し | 生データを自社の分析ツールや長期保存に回す |
| ユーザー管理 API | ライセンス(シート)の情報。利用状況のデータには含まれないので、こちらで取る |

ダッシュボードは、企業アカウントの **Insights タブ** から開く形で説明されています。ROIの推計はダッシュボードだけにあり、APIとNDJSONの書き出しには含まれません。

## 主な指標の公式の定義

[指標の一覧](https://docs.github.com/en/copilot/reference/copilot-usage-metrics/copilot-usage-metrics)と[数字の突き合わせ方](https://docs.github.com/en/copilot/reference/copilot-usage-metrics/reconciling-usage-metrics)のページの定義を、日本語にしたものです(2026年11月23日確認)。

| 指標 | 公式の定義 | APIの項目の例 |
| --- | --- | --- |
| 日次アクティブユーザー | その日に Copilot を使った人の数(重複なし) | daily_active_users |
| 週次アクティブユーザー | 7日間に Copilot を使った人の数(重複なし) | weekly_active_users |
| 合計のアクティブユーザー | 今の暦月に利用のあった、ライセンスを持つ人 | monthly_active_users |
| アクティブの判定 | その日にIDEで Copilot とやり取りした人を、その日のアクティブとする | user_initiated_interaction_count が1以上 |
| コード補完の採用率 | 提案のうち利用者が受け入れた割合。受け入れの数÷生成の数で計算 | code_acceptance_activity_count ÷ code_generation_activity_count |
| エージェントの利用率 | ライセンスを持つアクティブユーザーのうち、今の暦月にエージェントを使った人の割合 | — |
| チャットのモード別のリクエスト | 質問・編集・計画・エージェントのモードごとのリクエスト数 | — |
| AIで変更された行数 | 直近28日に、すべてのモードで追加・削除された行数 | loc_added_sum、loc_deleted_sum |
| エージェントの寄与 | 追加・削除された行のうち、エージェント(編集・エージェント・カスタムモード)によるものの割合 | — |
| プルリクエスト | その日に作成・レビュー・マージされた数、マージまでの時間の中央値(分)、Copilot のエージェントが作ったものやコードレビューを受けたものの数 | total_created、total_merged、median_minutes_to_merge、total_created_by_copilot |

採用率の「受け入れ」には、適用・挿入・コピーのボタンの操作が数えられ、OSのクリップボードで手で写した分は数えられないと書かれています。

### 利用の段階(コホート)の定義

impact ダッシュボードは、利用者を使っている機能の幅で4つに分けます。直近28日のうち**2日以上**使った機能を「使っている」とみなし、毎日計算し直すため、同じ人の段階が日によって変わることがあると書かれています。

| 段階 | 公式の条件 |
| --- | --- |
| Chat-first(APIでは No Cohort) | 下の段階の条件になる機能を使っていない。利用がないという意味ではなく、チャットだけの人もここに入る |
| Phase 1(コード補完が中心) | コード補完か、エージェントによる編集を使っている |
| Phase 2(エージェントが中心) | Copilot CLI・Copilot のクラウドのエージェント・Copilot のコードレビューのうち、ちょうど1つを使っている |
| Phase 3(複数のエージェント) | Copilot のアプリを使っているか、Phase 2 の対象を2つ以上使っている |

段階は機能の幅を表すもので、使った量ではありません。コード補完をたくさん使う人でも Phase 1 のままのことがある、と説明されています。impact ダッシュボードの「adoption multiplier」は、Phase 1〜3 の人と Chat-first の人で、1人あたり月のマージ数とマージまでの時間を比べたものです。

## 見誤りやすい点(GitHub自身が書いている注意)

[指標の読み方](https://docs.github.com/en/copilot/reference/copilot-usage-metrics/interpret-copilot-metrics)などのページには、数字の読み方についての注意がはっきり書かれています。導入効果を報告するときに特に大事なものを挙げます。

1. **採用率は生産性そのものではない。** 採用率の上昇は「信頼と有用性が高まっている」兆候、低下は提案が合っていないか作業の流れに引っかかりがある兆候として扱われています。下がったときは、IDEと拡張機能のバージョンを確かめるよう書かれています。
2. **プルリクエストとの関係は因果ではない。** impact ダッシュボードの比較は、別々の人の集団を比べたものです。GitHub は、チームの構成・案件の難しさ・経験年数も結果に影響しうると書いています。
3. **生成されたコードの量は成果の証明ではない。** 公式の報告のガイドは、生成されたコードが増えたことを、生産性・品質・届けた価値が上がった証拠として扱わないよう書いています。行数は「方向を示す目安」とされています。
4. **IDEの送信設定(テレメトリ)が切れている人は内訳に出ない。** IDEのテレメトリを切った人、プロキシやファイアウォールで送信先が遮られている人、対応していないIDEの人は、IDE別・機能別・行数の内訳に出ません。古いクライアントでは利用が少なく数えられることもあります。
5. **組織の数字を足しても企業全体の数字にはならない。** 企業のレポートは1人を1回として数えますが、組織のレポートは重複を除かないため、1人が複数の組織に出ます。日次アクティブユーザーを28日分足しても、28日間の利用者数にはなりません。
6. **ROIは推計。** impact ダッシュボードのROIは、使ったAIクレジットにもとづく推計で、APIでは取れません。期間を比べるときは同じ給与帯の前提で比べるよう書かれています。
7. **最近の日は低く見える。** 処理が終わるまで、直近の日の数字は少なく見えることがあると書かれています。

## 導入前後の比べ方(手順)

GitHub の公式ガイド「[会社の目標を Copilot で達成する](https://docs.github.com/en/copilot/get-started/achieve-company-goals)」「[Copilot の効果を測って示す](https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/measure-copilot-impact)」「[効果を伝える](https://docs.github.com/en/enterprise-cloud@latest/copilot/tutorials/roll-out-at-scale/communicate-copilot-impact)」の内容を、作業の順に並べました。

1. **目標を1〜2個に絞って決める。** 公式ガイドは、指標を選ぶ前に、改善したい開発の成果を1〜2個決めてチームに伝えるよう書いています。例として挙げられているのは、テストのカバー率、プルリクエストの速さ(リードタイム・レビューの往復・マージまでの時間・リリース後の不具合)、セキュリティの課題の残数、本番の障害、開発者の満足度です。
2. **導入を変える前に基準の数字を記録する。** 「Record a baseline before changing your rollout」と書かれています。プルリクエストのマージ数やマージまでの時間など、Copilot と関係なく取れる数字を残します。対象のリポジトリとツールの範囲も記録しておきます。
3. **ポリシーを有効にし、データの取り方を決める。** 企業の「Copilot usage metrics」のポリシーを有効にし、ダッシュボード(28日の移動期間)を見るのか、API(1日ごと・1人ごと)を取り込むのかを決めます。ダッシュボードと比べるなら、集計の期間を28日にそろえるとずれが少ないと書かれています。
4. **一部のチームから始める。** 全員に一斉に入れると、繁忙期やリリース前などの事情と区別できません。似た仕事をしているチームを分けて、先に入れるチームと後から入れるチームを作ると比べやすくなります(これは当サイトの整理で、公式ガイドは「同じチームを同じ報告期間で比べる」ことを求めています)。
5. **利用が定着したかを先に確かめる。** 週次アクティブユーザー÷ライセンス数が低いままなら、成果を論じる前に、設定・研修・ライセンスの割り当てを見直す段階です。チーム単位の数字は、ユーザーとチームの対応のレポートと、1人ごとのレポートをつないで作ると書かれています(5席未満のチームは対応のレポートに出ません)。
6. **同じ物差しで比べる。** 比べる期間・チーム・案件の種類・指標の定義をそろえます。人員の変化、案件の難しさ、リリースの予定、研修など、ほかの変化がなかったかも確かめます。速さと一緒に品質も見ます。
7. **アンケートや振り返りで補う。** ダッシュボードの傾向を、アンケートや振り返りと組み合わせるよう書かれています。「どの作業が楽になったか」「かえって手間が増えた作業はあるか」を聞くと、数字の理由が分かります。
8. **複数の期間を見てから広げるかを決める。** 公式ガイドは、複数の報告期間を比べ、開発者の声を集めてから、利用を広げるかを決めるよう書いています。

基準の数字がない場合は、公式ガイドに「そう書くこと」とあります。いちばん早い信頼できる期間から推移を追い、導入前後の比較としては示さないよう書かれています。

## 費用の側の数字:席の1年の総額

効果を報告するときは、使った席の費用も並べます。公式ガイドは、費用の数字は利用状況のテレメトリではなく請求の画面から取り、AIクレジットの消費と実際の請求額を分けて書くよう求めています。

下の表は、席の料金(Business 1席月19ドル・Enterprise 1席月39ドル、2026年11月22日確認)を12か月払い、日本でカードかPayPalで払う場合の消費税10%を足したものです。円は**1ドル=150円**で換算した目安で、含まれる分を超えたAIクレジットの従量料金は入れていません。

| 席の数 | Business 1年(税抜) | Business 1年(税込) | 円の目安 | Enterprise 1年(税込) | 円の目安 |
| --- | --- | --- | --- | --- | --- |
| 5席 | 1,140ドル | 1,254ドル | 約188,100円 | 2,574ドル | 約386,100円 |
| 10席 | 2,280ドル | 2,508ドル | 約376,200円 | 5,148ドル | 約772,200円 |

## 報告で使うときのまとめ方の例

- **何を決めるための報告か**: 更新するか、広げるか、研修を足すか。公式ガイドは、決めることと目標から書き始め、最後に推奨・担当者・成功の基準・次の見直しの日を置く形を示しています。
- **使われているか**: 週次アクティブユーザー ÷ ライセンス数、利用の段階ごとの人数の推移
- **成果が変わったか**: 基準の期間と比べた、プルリクエストのマージ数とマージまでの時間(先に入れたチームと後から入れたチームの差も併記)、品質の指標
- **費用**: 請求の画面の金額と、AIクレジットの消費を分けて
- **限界**: 「関連であって因果ではない」「テレメトリが切れている人は内訳に含まれない」「改善しなかった指標」を明記する

公式ガイドは、生成したコードや自己申告の時間の短縮を、そのまま金額の効果に換算しないよう書いています。節約の見積もりを入れる場合は、前提を書き、経理と確かめ、「ほかの仕事に回せた時間」と「実際に減った支出」を分けるよう求めています。

## 公式に書いていないこと

- **採用率やアクティブ率の合格ライン**: 週次アクティブユーザーの60%は「健全さの目安」とされていますが、目標値として扱わないよう書かれています。採用率の基準値は示されていません。
- **導入でどれだけ速くなるかの数字**: 確認したドキュメントには、導入した組織の平均的な改善の数字はありません。業界との比較の機能はありますが、関連であって因果ではないとされています。
- **企業アカウントに属さない組織での使い方**: 組織のAPIは用意されていますが、ポリシーの説明は企業の単位で書かれています。企業に属さない組織での有効化の手順は、確認したページでは読み取れませんでした。
- **2025年10月10日より前のデータ**: API の企業・ユーザーの1日ごとのレポートはこの日からです。それより前の比較の材料は、プルリクエストの記録など別の手段で残す必要があります。

## よくある質問

**Q. 個人のプランでもダッシュボードは使えますか。**
この記事で確認した公式ドキュメントは、企業(Enterprise)や組織の所有者・管理者が使う前提で書かれています。APIを呼べるのも、企業の所有者・請求の管理者、組織の所有者と、指標を見る権限を与えられた人です。個人で使っている場合の確認方法は、GitHub の最新のドキュメントを確認してください。

**Q. 提案の採用率は何%なら良いのですか。**
公式ドキュメントでは採用率の合格ラインは示されておらず、上がっていれば信頼と有用性が高まっている兆候、下がれば提案が合っていないか作業の流れに引っかかりがある兆候、という読み方が示されています。言語や作業内容で大きく変わるため、他社の数字と比べるより、自社の推移を見る方が意味があります。

**Q. データはいつから、どのくらい前までさかのぼれますか。**
REST API のドキュメントでは、企業とユーザーの1日ごとのレポートは2025年10月10日の分からあり、今日から最長1年さかのぼれると書かれています。ある日のデータは、その日が終わってからUTCで丸2日以内に使えるようになります(2026年11月23日確認)。長く比べるなら、NDJSONで書き出して自社で保存しておきます。

**Q. AIで書かれた行数が増えたら、生産性が上がったと言えますか。**
言えません。公式の報告のガイドは、生成されたコードが増えたことを、生産性・品質・届けた価値が上がった証拠として扱わないよう書いています。行数は方向を示す目安として、プルリクエストの速さや品質の指標と並べて見ます。

**Q. ほかのAIコーディングツールと比べるには。**
ツールごとに取れる指標が違うため、同じ物差しで比べるには、プルリクエストの数やマージまでの時間など、ツールに依存しない数字を使います。ツールそのものの違いは[GitHub Copilotの記事](/reviews/github-copilot-review/)、[Cursorの記事](/reviews/cursor-review/)、[AIコーディングツールの比較](/reviews/ai-coding-tools-comparison/)を参照してください。
